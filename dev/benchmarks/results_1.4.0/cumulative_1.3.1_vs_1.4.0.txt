Cumulative benchmark: tabxplor 1.3.1 (CRAN, installed) vs 1.4.0-dev (load_all)
=============================================================================
Same machine (Ryzen 7 5800X, 8 physical / 16 logical), R 4.5.1. Direct A/B in two processes:
1.3.1 = library(tabxplor); 1.4.0 = devtools::load_all(). median of system.time() over N reps.
API bridge: 1.3.1 merges via tab_many(..., compact=TRUE); 1.4.0 via tab(...). list = compact=FALSE
/ output_list=TRUE. tab_num() identical name in both.

## A. Factor "many tables" workflow -- gss_cat 21 483 rows, 5 row_vars x 3 col_vars (15 tables),
##    pct="row", color="diff", chi2=TRUE
  fixture                         1.3.1     1.4.0    speedup
  merged (default tab())          1.780 s   0.590 s   3.0x
  list (output_list / compact=F)  1.270 s   0.610 s   2.1x

## B. Base + parallel STACKING -- 43k rows, 8 factor row_vars x 2 col_vars, chi2=TRUE, list output
  1.3.1 serial                    1.390 s            (baseline)
  1.4.0 serial                    0.720 s   base gain    1.93x
  1.4.0 parallel W=8 (warm pool)  0.270 s   parallel     2.67x  (over 1.4.0 serial)
  ------------------------------------------------------------------
  TOTAL 1.3.1 -> 1.4.0 parallel   1.390 -> 0.270 = 5.15x  == 1.93 x 2.67 (MULTIPLICATIVE)
  => base improvements and parallelisation STACK. They are orthogonal axes: base shrinks the
     per-table O(cells) work; parallel runs the (already cheaper) per-row_var tables concurrently.
  Caveat: parallel has fixed overhead (cold pool warm ~1 s, data ship once, result serialisation),
  so the multiplier is realised only for MANY tables + a warm/reused pool; for a few tables or
  trivial per-table work it shrinks (Amdahl on the serial merge/ship part). mirai workers must run
  the SAME source (installed pkg, or a load_all pre-warm) -- else a version mismatch errors.

## C. Numeric means, large data -- ~8.0M rows (gss_cat replicated 372x), tab_num(age, tvhours)
  fixture                         1.3.1     1.4.0    speedup
  weighted, few groups            0.330 s   0.390 s   ~flat
  weighted, many groups           0.650 s   0.630 s   ~flat
  unweighted, many groups         0.300 s   0.320 s   ~flat
  => On TYPICAL survey numerics (low-cardinality age/tvhours) the wall-time is ~unchanged.
  The large documented numeric win (Phase 2: tab_num 5.6x unweighted / 8.3x weighted, 6-11x less
  ALLOCATION, dev/benchmarks/results_1.4.0/before_phase2_8M.csv vs after_rollup_8M.csv) is on a
  HEAVIER continuous-numeric synthetic 8M fixture (gen_big_df) that stressed the old weighted.var
  double-scan; it does not generalise to light categorical-survey numerics on wall-time, though the
  allocation-churn reduction (moment sums vs weighted.var) holds regardless.

## D. Single big factor table -- 2M rows, tab(marital, race, wt=w, pct="row")
  1.3.1  0.080 s | 1.4.0  0.060 s | ~1.3x (already fast in 1.3.1; big single count tables were
  never the bottleneck -- the factor gains live in the many-small-tables O(cells) path, A/B).

## Bottom line (cumulative 1.3.1 -> 1.4.0)
- Many exploratory factor tables (the core workflow): ~2-3x faster serial, ~5x with parallel=8.
- Base + parallel stack multiplicatively.
- Numeric means: ~flat on typical survey data (wall-time); large only on heavy continuous numerics;
  allocation churn always much lower.
- Big single factor tables: already fast, ~unchanged.
