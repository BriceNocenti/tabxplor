Phase 7d-ii -- the three-stage carve. Perf verification.
=========================================================

The carve splits tab_build() into five stages (tab_setup -> tab_prepare_pop -> tab_aggregate ->
tab_transform -> tab_assemble) threading a `ctx` list. It is a RELOCATION, not a rewrite: the same
calls in the same order. tab_build() runs ONCE per tab() call and pmaps over row_vars/col_vars
internally, so the carve's extra work (5x list2env + 4x ctx_update on a ~40-element list) is O(1)
per call -- microseconds, negligible against the per-table fmt/chi2 work.

Fixture: forcats::gss_cat (21,483 rows). Warm, then 200 iterations, elapsed / 200.
Command: tab(gss, marital, race, pct = "row", color = "diff")

  CARVED    single tab() x200:  9.660 s   48.30 ms/call
  ORIGINAL  single tab() x200:  9.590 s   47.95 ms/call
  delta:    +0.35 ms/call (+0.7%)  -- within run-to-run noise.

Byte-identity: full suite green (1150 pass, 0 fail), NO golden regeneration. test-golden.R,
test-fuse-parity.R, test-num-fuse-parity.R, test-counts-parity.R all unchanged and green; new
test-carve-parity.R (stage composition == tab_build + the 7e seam contract) and test-cache-keys.R
(the tab_resolve_settings $cache_keys shape) green.

Batch reference (informational; 4 row_vars x 1 col_var, weighted, diff + ci = diff + chi2, x10):
  ~673 ms/call -- dominated by per-table chi2 + fmt (N-independent), as expected.

Note: the pre-existing "pct can't be recycled" error on multi-row_var x multi-col_var + scalar pct
(e.g. tab(gss, c(a,b,c), c(x,y,z), pct = "row")) reproduces identically on the pre-carve code -- it
is NOT a carve regression; out of scope for 7d-ii.
