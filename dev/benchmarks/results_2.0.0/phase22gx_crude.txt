Phase 22g-x -- the crude block's own cache, measured (dev/benchmarks/phase22gx_crude.R)
WSL2 / Ubuntu 26.04, 12 cores, R 4.6.1, gss_cat (21 483 rows), OMP_NUM_THREADS=1, min of 3 runs.
BEFORE = the same script run against a pristine HEAD (git archive HEAD | tar -x -C <tmp>).

=== 1. what the crude block costs a SERVED build (empirical TRUE minus FALSE, both warm) ===

                                     ---------- BEFORE ----------   ---------- AFTER ----------
  case                                 emp=T   crude  share           emp=T   crude  share
  binomial, factors + 1 numeric        0.266   0.071    27%           0.235   0.038    16%
  binomial, 3 numeric predictors       0.127   0.070    55%           0.087   0.030    34%
  binomial, marginal RD                0.454   0.251    55%           0.428   0.219    51%
  multinomial, factors + 1 numeric     3.624   1.858    51%           2.009   0.127     6%
  multinomial, marginal RD            32.723  30.973    95%          18.476  16.733    91%

  The concentrated win is the multinomial: its crude block goes 1.858 s -> 0.127 s (x15), and the
  whole served build 3.624 -> 2.009 (x1.8). An ordinary binomial saves ~0.03 s, i.e. nothing a user
  can feel -- as scoped.

  ⚠ THE MARGINAL ROWS ARE THE LIMIT, AND IT IS THE RIGHT ONE: only the FIT is cached, and a marginal
  crude row is a reg_marginal() sweep per predictor, which is ESTIMAND-dependent and must be
  recomputed. So `effect = "marginal"` keeps most of its crude cost (16.7 s of the multinomial's
  18.5), and a multinomial marginal table is still the panel's slowest shape by an order of
  magnitude. Caching the SWEEP would need a second key carrying the estimand; not this phase.

=== 2. the store: one record per model + one per NON-SATURATED crude predictor ===

  case                                BEFORE          AFTER
  binomial, factors + 1 numeric       1 / 29.3 KB     2 /  44.4 KB
  binomial, 3 numeric predictors      1 / 24.2 KB     4 /  70.3 KB
  binomial, marginal RD               1 / 29.3 KB     2 /  44.4 KB
  multinomial, factors + 1 numeric    1 / 92.4 KB     2 / 114.4 KB
  multinomial, marginal RD            1 / 92.4 KB     2 / 114.4 KB

  A crude record is the same ~15-22 KB shape as a model one, in the same "fit" tier, against a 32 MB
  store budget. An ALL-FACTOR block on a flat design is saturated and fits nothing, so it adds no
  record at all -- the cache is inert exactly where there was no cost.

=== 3. one interaction, on a warm store (s / cache hits) ===

  -- binomial, factors + 1 numeric        BEFORE          AFTER
  re-apply                                0.251  1        0.221  2
  measure + effect                        0.436  1        0.400  2
  reorder (not the first)                 0.315  0        0.220  2      <- a HIT now
  reorder onto the first                  0.311  0        0.309  0      <- the reference: a refit
  multiplier                              0.312  0        0.309  0
  conf_level                              0.245  1        0.224  2

  -- multinomial, factors + 1 numeric     BEFORE          AFTER
  re-apply                                3.470  1        1.846  2
  measure + effect                       33.526  1       19.497  2
  reorder (not the first)                14.818  0        1.854  2      <- x8
  reorder onto the first                 14.555  0       14.742  0
  multiplier                             14.709  0       14.771  0
  conf_level                              3.402  1        1.869  2

  THE DROP-DOWN LATENCY IS THE RE-RUN, NOT THE WIDGET. Every var-table pick writes an option that is
  in .opts(), so it re-runs the analysis; fetchLevels() caches per variable and never repeats, and a
  `ref` pick's own handler is a bare option write. So the rows above ARE the latency, and the two
  that stay slow stay slow for a reason:
    * `ref =`   changes which level the others are compared to -> an honest refit.
    * `shape =` changes the column -> an honest refit.
    * `multiplier` is a REPORTING choice, yet it sits in the key, because reg_tidy_rescale() runs
      inside reg_fit() and `tidy_native` comes out already scaled. Moving that rescale into
      reg_tidy_finalize() would let it leave the key exactly as the estimand did in Phase 22j
      (14.7 s -> ~1.9 s on a multinomial). It interacts with the profile bounds, which ride natively
      on the record, and with reg_digest_revive()'s recipe -> recorded under Phase 22x, not built.
